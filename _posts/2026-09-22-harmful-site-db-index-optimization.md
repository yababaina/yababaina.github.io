유해사이트 등급 DB를 네트워크 장비에서 실시간으로 조회해야 하는 요구사항이 있었습니다. 원본 DB는 약 **350MB**였고, 그대로 메모리에 올리거나 해시테이블로 만들면 메모리 사용량과 초기화 시간이 모두 부담이 됩니다.

이 글에서는 DB를 **Bloom filter + MPHF(PTHash)** 기반의 전용 바이너리 인덱스로 변환해 해결한 과정을 정리합니다. 자료구조로 MPHF + Bloom filter를 고른 이유는 [이전 글의 벤치마크]({% post_url 2026-09-22-grade-db-data-structure-benchmark %})에 정리했습니다.

**결과 요약**

- 약 350MB 규모의 DB를 **약 17MB 바이너리 인덱스**로 변환 (데이터 크기 **약 95% 절감**)
- 초기화 시간: 런타임 빌드 2,276ms → 사전 빌드 인덱스 로드 **26.6ms**
- 조회 시간: hit **269ns**, miss **214ns**
- DPI에서 추출한 Host 정보로 **실시간 유해사이트 판정**

**목차**

1. MPHF(PTHash) 개념과 한계
2. 구성: 생성 툴과 인덱스 파일
3. 인덱스 바이너리 구조
4. 등급 데이터 비트 패킹
5. 조회 흐름
6. 성능 테스트 결과

# 1. MPHF(PTHash) 개념과 한계

## MPHF(Minimal Perfect Hash Function)란?

미리 정해진 키 집합 *S*(크기 *n*)의 각 키를 `[0, n)` 범위(0 이상 n 미만)의 서로 다른 정수로 **1:1 매핑**하는 해시 함수입니다.

일반 해시테이블은 충돌 처리를 위해 키를 함께 저장해야 합니다. 반면 MPHF는 **키를 저장하지 않고**, 키 집합과 `[0, n)` 사이의 대응 관계를 계산하는 **함수 자체만 저장**합니다. 그래서 키 개수가 많을수록 공간 이득이 커집니다.

## PTHash

MPHF 구현체로는 [PTHash](https://github.com/jermp/pthash)를 사용했습니다. 키당 약 2~3비트 수준의 작은 공간으로 빠른 조회를 목표로 설계된 라이브러리입니다.

- *PTHash: Revisiting FCH Minimal Perfect Hashing* (Pibiri & Trani, SIGIR 2021)
- *Parallel and External-Memory Construction of Minimal Perfect Hash Functions with PTHash* (IEEE TKDE 2024)

## 한계

1. **오탐 가능성**
    - 빌드 시점 키 집합 *S*에 없는 키를 넣어도 `[0, n)` 범위의 임의의 인덱스를 반환합니다. 반환값이 유효한지는 스스로 보장하지 않습니다.
2. **느린 빌드 속도**
    - 버킷 내 키들이 충돌 없이 서로 다른 빈 슬롯으로 매핑되는 시드값(pilot)을 찾을 때까지 반복 탐색합니다.
    - 키 개수가 많을수록 빌드 시간이 길어집니다.
3. **런타임 빌드 시 메모리 급증**
    - 런타임에 빌드하면 원본 DB 전체를 메모리에 올려야 하므로 순간적으로 메모리 사용량이 급증하고, OOM 위험이 있습니다.

## 해결 방법

**1. 오탐: Bloom filter + fingerprint로 이중 검증**

- 조회 앞단에 **Bloom filter**를 두어, DB에 없는 대부분의 키를 MPHF 조회 전에 걸러냅니다.
- 각 인덱스 슬롯에 해당 키의 **XXH3 64비트 fingerprint**를 저장해 두고, 조회 시 질의 키로 다시 계산한 fingerprint와 비교합니다. 다르면 miss로 판정합니다.
- 최종 오탐률은 Bloom filter 오탐률과 fingerprint 충돌 확률(2⁻⁶⁴)의 곱으로 근사되며, 사실상 무시할 수 있는 수준입니다.

```
최종 오탐률 ≈ 0.001 × 5.42×10⁻²⁰ ≈ 5.42×10⁻²³
```

**2. 빌드 속도, 메모리: 오프라인 사전 빌드**

- MPHF를 런타임에 빌드하지 않고, **오프라인에서 미리 빌드한 바이너리를 모듈이 로드**하는 방식을 택했습니다.
- Bloom filter도 같은 바이너리에 포함해 배포 단위와 구현을 단순화했습니다.

# 2. 구성: 생성 툴과 인덱스 파일

```
원본 DB ──> [인덱스 생성 툴] ──(오프라인)──> 인덱스 파일 ──(배포, 로드)──> 조회 모듈
                   │                                                     │
                   └────────── 공유 헤더 (포맷 정의, 컴파일 타임) ─────────┘
```

- **인덱스 생성 툴**: 원본 DB를 읽어 Bloom filter, MPHF, fingerprint, 등급 데이터를 만들고 하나의 바이너리 파일로 저장합니다.
- **조회 모듈**: 인덱스 파일을 로드해 조회만 합니다. 무거운 빌드 작업은 하지 않습니다.
- **공유 헤더**: 두 쪽이 같은 포맷 정의를 쓰도록 컴파일 타임에 함께 include합니다. 포맷이 바뀌어도 한 곳만 고치면 됩니다.
- DB 종류별로 인덱스 파일을 따로 만들어 로드합니다.

# 3. 인덱스 바이너리 구조

ELF가 "ELF Header + 섹션들"로 구성되듯, 인덱스 파일도 **고정 크기 헤더 + 섹션들**로 구성했습니다.

```
+----------------------------------------------+
| Header (고정 크기)                            |
|  - 포맷 식별자, 버전, 키 개수 등 메타데이터   |
|  - 무결성 검증용 해시                         |
|  - 섹션 테이블: 섹션별 {offset, size}         |
+----------------------------------------------+
| Bloom filter 섹션                             |
+----------------------------------------------+
| MPHF 섹션 (직렬화된 MPHF)                     |
+----------------------------------------------+
| Fingerprint 섹션 (키별 XXH3 64bit)            |
+----------------------------------------------+
| 등급 섹션 (키별 비트 패킹된 등급 데이터)      |
+----------------------------------------------+
```

설계하면서 신경 쓴 부분은 다음과 같습니다.

- **섹션 테이블**: 헤더에 섹션별 offset과 size를 기록해, 모듈은 헤더만 읽으면 필요한 섹션으로 바로 찾아갈 수 있습니다.
- **정렬**: 각 섹션을 경계에 맞춰 정렬해 로드 후 바로 배열로 접근할 수 있게 했습니다.
- **고정 크기 헤더**: `static_assert`로 헤더 크기를 컴파일 타임에 강제해, 생성 툴과 모듈의 포맷이 어긋나지 않도록 했습니다.
- **검증**: 포맷 버전과 무결성 해시를 확인해, 버전이 맞지 않거나 전송 중 손상된 파일은 로드하지 않습니다.
- **선택적 섹션**: 매칭되면 무조건 차단하는 DB는 등급 데이터가 필요 없으므로 등급 섹션을 생략합니다.

# 4. 등급 데이터 비트 패킹

원본 DB의 한 row에는 키(Host MD5) 외에도 여러 필드가 들어 있습니다. 이 중 **차단 판정에 필요한 등급·플래그 값만 골라 `uint32_t` 하나에 비트 패킹**하고, 나머지는 버립니다.

- 각 값의 범위에 맞춰 필요한 만큼만 비트를 할당 (예: 0~5 범위 값은 3bit, 참/거짓 값은 1bit)
- 실제로 쓰는 비트는 16bit 정도라 `uint32_t` 하나에 여유 있게 들어감
- 키는 32자 hex 문자열을 16바이트 바이너리로 변환해 Bloom filter / MPHF의 키로만 사용

원본에서 한 row당 수십 바이트를 차지하던 데이터가, 인덱스에서는 **fingerprint 8바이트 + 등급 4바이트 + MPHF·Bloom filter의 키당 몇 비트** 수준으로 줄어듭니다. 이것이 350MB → 17MB 감소의 핵심입니다.

# 5. 조회 흐름

## 초기화

1. DB별 인덱스 파일을 로드합니다.
2. 헤더를 읽어 섹션별 데이터(Bloom filter, MPHF, fingerprint, 등급 비트)를 메모리의 조회용 객체로 복사합니다.
3. 파일을 읽기 위해 쓴 임시 버퍼는 복사가 끝나면 자동으로 해제됩니다.

## 조회

DPI에서 추출한 Host 정보가 들어오면 MD5로 변환한 뒤 다음 순서로 탐색합니다.

```
Host ──MD5──> key
               │
               ▼
        [Bloom filter] ── 없음 ──> miss (false)
               │ 있을 수 있음
               ▼
          [MPHF] ──> slot index
               │
               ▼
     [fingerprint 비교] ── 불일치 ──> miss (false)
               │ 일치
               ▼
       hit: 등급 비트 + true 반환
```

대부분의 정상 트래픽은 DB에 없는 Host이므로 Bloom filter 단계에서 바로 걸러집니다. 따라서 miss 경로를 짧게 유지하는 것이 전체 처리량에 중요합니다.

# 6. 성능 테스트 결과

## 테스트 조건

- 등급 DB만 적용해, 초기 방식(원본 DB를 런타임에 읽어 MPHF 빌드)과 같은 조건에서 비교
- 컴파일 플래그 `-O0`과 `-Og` 두 가지로 측정
- **시간 측정**
    - `std::chrono::steady_clock` 사용
    - 전체 iteration 총 소요 시간을 iteration 수로 나눈 단순 평균
- **메모리 측정**
    - `/proc/self/status`의 `VmRSS` 값을 로드 전/후, 조회 전/후에 각각 읽음
    - 측정 직전 `malloc_trim(0)`을 호출해, 실제로 반환된 메모리를 기준으로 보정

## 결과

| 항목 | 런타임 빌드 (초기 방식) | 사전 빌드 로드 `-O0` | 사전 빌드 로드 `-Og` |
| --- | --- | --- | --- |
| RSS | 16.1 MiB | 17.45 MiB | 17.27 MiB |
| load / init | 2,276 ms | 91.2 ms | **26.6 ms** |
| lookup hit | 641 ns | 589 ns | **269 ns** |
| lookup hit /s (환산) | 1,560,062/s | 1,697,793/s | **3,717,472/s** |
| lookup miss | 148 ns | 276 ns | 214 ns |
| lookup miss /s (환산) | 6,756,757/s | 3,623,188/s | 4,672,897/s |

- **초기화 시간**은 런타임 빌드를 없애면서 2,276ms → 26.6ms로 약 **85배 단축**되었습니다. 런타임 빌드 시의 순간 메모리 급증도 사라졌습니다.
- **lookup hit**은 `-Og` 기준 269ns로, 초당 약 370만 건을 처리할 수 있습니다.
- RSS는 초기 방식과 거의 같습니다. 사전 빌드 방식에는 fingerprint와 등급 섹션이 추가되었지만 큰 차이가 없습니다.
- **lookup miss**는 초기 방식보다 조금 늘었습니다.
    - DB별로 튜닝할 수 있도록 Bloom filter의 비트 수를 컴파일 타임 상수에서 런타임 변수로 바꾸면서, 컴파일러의 상수 나눗셈 최적화가 빠진 것이 원인으로 추정됩니다.
    - miss 경로는 대부분 Bloom filter에서 끝나기 때문에 이 비용이 그대로 드러납니다.

실제 운영처럼 DB 두 종류를 **모두 로드했을 때 RSS는 약 24MiB(24,612KB)**였습니다.

# 마무리

정리하면 다음과 같은 구조가 되었습니다.

- 원본 DB가 갱신되면 서버에서 인덱스 파일을 생성해 장비로 배포
- 장비의 DPI 엔진이 인덱스 파일을 로드하고, 트래픽에서 추출한 Host로 실시간 유해사이트 판정
